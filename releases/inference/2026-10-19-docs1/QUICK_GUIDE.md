# Quick guide: GLM, DeepSeek and Qwen on Leonardo

Use the same shared scripts for all three models. Select a profile; the launcher chooses its checkpoint, parallelism and registered runtime. Model weights and the SIF are not downloaded by these steps.

| Profile | Served model | Parallelism | Default local port |
| --- | --- | --- | --- |
| `qwen235b` | `qwen3-235b-a22b-fp8-leonardo` | TP4 / PP2 | `18085` |
| `glm53` | `glm-5.3-flash-leonardo` | TP4 / PP2 | `18083` |
| `deepseek41` | `deepseek-v4.1-flash-1017-leonardo` | TP8 / PP1 + EP; Engram CPU offload | `18084` |

Each profile requests **two nodes and eight A100 GPUs**, 480GB host RAM per node and up to two hours. Context is limited to 2048 tokens. Qwen and GLM have four sequence slots; DeepSeek has two, so four concurrent requests can be queued.

Qwen passed fresh common-launcher validation in job `61389137`: seven English API checks at startup and two repeat SSH client suites. Its observed cold start to a healthy API was **7.0 minutes**, excluding queue time. GLM and DeepSeek passed the same API suites on 18 October; their earlier observed starts were 13.3 and 25.8 minutes. Storage, cache and queue conditions can change these timings.

This release fixes a job-number-dependent overlap between API and distributed-master ports. Qwen validates the corrected launcher on GPUs. GLM/DeepSeek engine settings and Python execution code are unchanged, but those two models were not GPU-rerun after this port-only correction. See `GPU_VALIDATION.json` and `PRIOR_VALIDATION.md`. All GPU checks so far use one operator account; other accounts and sustained application load remain unvalidated.

## 1. Server operator: prepare on Leonardo

Use your own Leonardo account and coordinate one team server at a time:

```bash
ssh YOUR_LOGIN@login01-ext.leonardo.cineca.it
```

On Leonardo, set `BASE` to the existing team installation. This public example uses a generic name:

```bash
BASE="$WORK/team_vllm"
MODEL=qwen235b
RUN_DIR=$(bash "$BASE/scripts/inference/prepare_run.sh" "$MODEL" --base "$BASE") && cd "$RUN_DIR"
```

Choose `glm53` or `deepseek41` instead for the other models. Preparation verifies the release hashes and readable assets, creates a private home-directory run, and generates a new session key. It does not submit a job. The selected source is pinned in `RUN_CONFIG.json`; submit from this private directory, never the shared release.

```bash
python3 inference.py info
python3 inference.py cpu-check
bash submit_server.sh --dry-run
bash submit_server.sh
cat .runtime/job_id
tail -f *-common-*.out
```

A permitted reservation can be supplied as `bash submit_server.sh --reservation NAME`. Wait for `INFERENCE_READY`: the server runs all seven English API checks before publishing the endpoint. A failed check withholds the endpoint and stops the allocation.

## 2. Locate the endpoint and session key

From the private run directory:

```bash
cat .runtime/endpoint.json
readlink -f .runtime/api_key
squeue -j "$(cat .runtime/job_id)"
```

`.runtime` lives inside your private `RUN_DIR`. The key is generated by `prepare_run.sh`, stored at `.runtime/api_key` with mode 600, and differs for every new run. View it only in your private terminal if needed:

```bash
cat .runtime/api_key
```

Give approved teammates the current `endpoint.json` and session inference key through an agreed private channel. Each client uses their own Leonardo login; the inference key does not replace SSH authentication. Keep keys, `.runtime`, run directories and caches out of shared folders and Git. Old test servers have been stopped; their endpoints and keys are no longer usable.

## 3. API client: download the code to your computer

No GPU, model weights or container is needed on the client:

```bash
git clone https://github.com/Jules0315/Guardrails-vllm.git
cd Guardrails-vllm/scripts/inference
```

For an existing clean clone, run `git pull --ff-only` from the repository root first. Save the operator's current endpoint as `endpoint.json` in your private local client directory. Enter the session key using the hidden prompt:

```bash
MODEL=qwen235b
PROFILE="profiles/$MODEL.json"
KEY_FILE=".runtime/$MODEL-api-key"
python3 client.py key --profile "$PROFILE" --key-file "$KEY_FILE"
python3 client.py tunnel --profile "$PROFILE" --endpoint endpoint.json --user YOUR_LOGIN
```

Keep the tunnel terminal open. In a second terminal in the same directory, set the same model and key-file path:

```bash
MODEL=qwen235b
PROFILE="profiles/$MODEL.json"
KEY_FILE=".runtime/$MODEL-api-key"
python3 client.py test --profile "$PROFILE" --key-file "$KEY_FILE"
python3 client.py chat --profile "$PROFILE" --key-file "$KEY_FILE"
```

Use `MODEL=glm53` or `MODEL=deepseek41` for another model. Key entry refuses to overwrite an existing file: choose a fresh key-file name for a new session, or remove your expired local key file first. Use that same filename with `key`, `test` and `chat`.

The helper binds SSH forwarding to localhost. Add `--local-port PORT` consistently to `tunnel`, `test` and `chat` to override the table's port. Closing the tunnel with Ctrl+C closes the local connection. Qwen requests use `enable_thinking=false`, so the basic tests inspect final responses rather than reasoning-only output. All included test/example prompts are in English.

The suite checks authentication, model catalog, exact arithmetic output, an English HPC introduction, SSE content plus `[DONE]`, forced function-call JSON and four concurrent requests. It inspects function-call output without executing the tool. Passing this basic suite does not establish production capacity or long-term availability.

## 4. Stop your server

On Leonardo, from its private run directory:

```bash
scancel "$(cat .runtime/job_id)"
```

The endpoint is removed on shutdown. A dead launcher or three failed health checks also stops the allocation. Slurm sends a termination signal about 90 seconds before allocation expiry. Clients still need timeouts and retries. Persistent/unattended authentication or alternative proxy tunnels require agreement with CINECA; this personal SSH workflow does not approve those routes.

## Shared layout and adding models

```text
scripts/inference -> ../releases/inference/<validated-release>
releases/inference/<release>/        code, profiles, QUICK_GUIDE and hashes
runtimes/<runtime>/<version>/        image.sif, python-overlay, runtime.json
inference-site.json                 site-owned project, queues and asset paths
users/<login>/<profile>--<runtime>/   private writable caches and temporary files
runs/<date>/job-<id>/                reviewed results without secrets
```

All current profiles use the registered `vllm-backport-sm80-0.13.1` runtime. Weights stay in their existing locations; Qwen currently uses a retained scratch checkpoint. If asset preflight reports missing files, contact the maintainer to verify the retained storage. A new container/runtime version gets a new ID and cache namespace. Never modify either path of a hardlinked SIF in place.

To add another supported vLLM model, register its checkpoint in the site configuration, add a JSON profile and choose a compatible runtime. Reuse the common launcher/client, add only a reviewed hook if needed, run model-specific GPU/API checks and publish a new immutable snapshot with hashes. Models lacking the suite's tool capability need a suitable capability-specific test suite. Historical individual Qwen scripts remain under the repository's `qwen/` directory; use this common profile for the current workflow.
